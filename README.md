# Telegram-чат через GREEN-API

Тестовое задание: веб-чат в духе web.telegram.org, который работает через [GREEN-API](https://green-api.com/telegram/docs/).
Вводите данные своего инстанса, открываете чат по номеру телефона, пишете — ответ собеседника приходит в тот же чат.

**Демо:** https://valary.github.io/green_api/ — кнопка «Открыть демо без данных» или сразу https://valary.github.io/green_api/?demo.
В демо ключи не нужны: запросы перехватывает MSW прямо в браузере, в GREEN-API ничего не уходит.

## Локальный запуск

Нужны git и Node.js 24 (версия лежит в `.nvmrc`; на 22 и 26 тоже работает).

```bash
git clone git@github.com:valary/green_api.git
cd green_api
nvm use            # или поставьте Node 24 любым удобным способом
npm ci
npm run dev        # http://localhost:5173
```

Откройте http://localhost:5173. Дальше два пути.

**Демо без ключей.** Нажмите «Открыть демо без данных». Создайте чат с любым номером, например `+7 900 123-45-67`, и отправьте сообщение:
через секунду-две придёт автоответ, у вашего сообщения появятся ✓ и ✓✓. Сценарии для проверки ошибок открываются параметром в адресе:

| Адрес              | Что происходит                                                                  |
| ------------------ | ------------------------------------------------------------------------------- |
| `/?demo`           | обычный сценарий                                                                |
| `/?demo=settings`  | у инстанса задан webhookUrl — появляется предупреждение                         |
| `/?demo=offline`   | через 5 с после входа пропадает связь на 20 с, потом приём продолжается сам     |
| `/?demo=sendError` | первая отправка падает, «Повторить» проходит                                    |
| `/?demo=newChat`   | через 3 с пишет незнакомый человек — в списке появляется новый чат со счётчиком |

Номер на `…0000` «не находится» в Telegram, номер на `…0466` упирается в лимит тарифа.

**Свой инстанс.** В [личном кабинете GREEN-API](https://console.green-api.com) откройте инстанс Telegram и скопируйте idInstance и apiTokenInstance.
Введите их в форму: apiUrl подставится сам по первым четырём цифрам idInstance (`1101000001` → `https://1101.api.green-api.com`),
если в кабинете указан другой адрес — поправьте поле. Если инстанс ещё не подключён к Telegram, приложение так и скажет:
подключите аккаунт по QR-коду (Telegram → Настройки → Устройства → Подключить устройство) и подождите, пока статус станет `authorized`, обычно до пары минут.

Чтобы входящие приходили, в настройках инстанса должно быть:

| Настройка         | Значение | Зачем                                          |
| ----------------- | -------- | ---------------------------------------------- |
| `webhookUrl`      | пусто    | с вебхуком очередь для HTTP API не наполняется |
| `incomingWebhook` | `yes`    | входящие сообщения                             |
| `outgoingWebhook` | `yes`    | статусы ✓✓                                     |

Приложение проверяет это после входа и подсказывает, что поменять. Само настройки не трогает: SetSettings перезапускает инстанс на несколько минут.

Про тариф Developer: 3 чата в месяц, поэтому пишите по номеру, а не по `номер@c.us` — для Telegram это съедает квоту дважды.
И не держите второй опросчик очереди (другой скрипт, вебхук): он будет забирать уведомления, и ответы «пропадут».

Остальные команды:

```bash
npm run build && npm run preview   # продакшен-сборка, http://localhost:4173
npm test                           # Vitest + Testing Library + MSW
npm run lint                       # ESLint
npm run check                      # lint + типы + тесты + сборка, как в CI
```

## Как устроено

Vite, React 19, TypeScript strict, Redux Toolkit, axios, react-hook-form + yup, styled-components, React Router, MSW.
Структура — Feature-Sliced Design, у каждого слайса публичный `index.ts`:

```
src/
  app/        провайдеры, стор, роутер, глобальные стили
  pages/      login, chat — только раскладка
  widgets/    chat-sidebar, chat-window, connection-banners
  features/   auth, logout, create-chat, send-message, receive-notifications
  entities/   session, chat, message
  shared/     api (axios + MSW-мок инстанса), ui, lib, theme, config
```

Путь сообщения. «Новый чат» нормализует номер и вызывает `checkAccount` — Telegram отвечает числовым chatId, и дальше
всё идёт только по нему: отправка, сопоставление ответов, склейка статусов. Отправленное сообщение сразу появляется в ленте
со статусом «отправляется», после ответа `sendMessage` получает idMessage. Приём — отдельный цикл в `features/receive-notifications`:
`receiveNotification` → разбор → `deleteNotification` → следующий запрос. Ровно один запрос в полёте, delete для каждого
уведомления, даже нераспознанного — иначе очередь встанет на нём навсегда. При сетевых ошибках пауза растёт 1 → 2 → 4 … 30 с,
на 401/403 цикл останавливается и предлагает войти заново, на постоянные 4xx (инстанс разлогинен, вебхук, лимит) показывает баннер.

Почему long polling, а не вебхук: сервера у приложения нет, а HTTP API GREEN-API отдаёт уведомления именно так.
`setInterval` не использую — запросы наслаивались бы друг на друга. Чтобы две вкладки не делили одну очередь,
опросчик берёт Web Lock на инстанс: вторая вкладка показывает «приём идёт в другой вкладке» и подхватывает его, когда первая закроется.

Одно и то же сообщение может прийти несколько раз, а эхо `outgoingAPIMessageReceived` и статусы иногда обгоняют ответ `sendMessage`.
Поэтому редьюсеры дедуплицируют по idMessage, склеивают эхо с отправленным сообщением и откладывают «ранние» статусы до появления id.
Это чистые функции, они покрыты тестами.

Где токен. У GREEN-API токен — часть пути запроса, поэтому URL собирается в одном месте, в request-интерцепторе axios.
В Redux токена нет (его не увидит DevTools), в адрес страницы он не попадает, из текста ошибок вычищается, `console` в коде запрещён линтером.
Без «Запомнить на этом устройстве» данные лежат в sessionStorage и исчезают с вкладкой, «Выйти» чистит оба хранилища.
Одно ограничение не обойти: при упавшем запросе браузер сам пишет его URL (с токеном) в консоль — не делитесь скриншотами вкладок Network и Console.

Моки. Одни и те же MSW-хендлеры работают и в тестах (`msw/node`), и в демо (`msw/browser`). Мок ведёт себя как настоящая очередь:
пока уведомление не удалено, `receiveNotification` отдаёт его снова. Поэтому демо и тесты гоняют настоящий код клиента и цикла приёма,
а воркер с хендлерами грузится отдельным чанком только в демо.

## Что бы улучшила

- Приём через свой небольшой бэкенд: вебхук GREEN-API → WebSocket в браузер. Это убирает long polling и токен из браузера совсем.
- Историю через `getChatHistory` при открытии чата — сейчас видно только то, что пришло за сессию.
- Виртуализацию ленты для длинных переписок.
- e2e на Playwright поверх того же демо-режима и прогон axe в CI.
- i18n: сейчас всё на русском, тексты ошибок собраны в одном месте, так что вынести их несложно.

## Деплой

GitHub Pages через Actions. В репозитории: Settings → Pages → Source: GitHub Actions, затем Actions → Deploy to GitHub Pages → Run workflow.
Workflow запускается только вручную (`workflow_dispatch`), base берёт из имени репозитория, так что сборка получается под `/green_api/`.
В сборку добавляется CSP-мета и `404.html` — копия `index.html`, чтобы прямые ссылки на чат открывались.
Проверить то же локально: `VITE_BASE=/green_api/ npm run build && npx vite preview --base /green_api/`.
